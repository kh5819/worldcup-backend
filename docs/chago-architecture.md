# 차고차고 (DUO Chago) — 분석 · 설계 · 개발 계획

작성: 2026-10-26 · 상태: **1단계(핵심 엔진)·2단계(실시간 멀티플레이)·3단계(AI 봇)·4단계(그래픽·UI·사운드)·5단계(게임성 강화) 구현·검증 완료 / 6단계(운영 기능) 미착수**
운영 서버 배포는 승인 전까지 하지 않는다. `index.js`에는 import 1줄 + register 2줄만 추가했고(로컬), 배포 전이라 운영에는 반영되지 않았다.
에셋은 **저작권 문제가 없는 것(CC0·퍼블릭 도메인)만** 허락받았다(2026-10-26). 4단계에서는 **외부 에셋을 하나도 쓰지 않고** 그래픽·사운드를 전부 코드로 직접 만들어 라이선스 이슈가 없다(아래 14장).

## 1. 기존 플레이듀오 시스템 분석

### 1-1. 기술 스택
| 영역 | 내용 |
|---|---|
| 프론트 | 빌드 도구 없는 정적 HTML + 바닐라 JS(ES 모듈). `홈페이지 제작/` 폴더. 파일명 뒤 `?v=날짜_번호`로 캐시 갱신. 배포는 Cloudflare Pages(`_worker.js`, `_headers`) |
| 백엔드 | Node 24 + Express 4 + socket.io 4.8, ESM. Render에서 실행(`onrender.com`). **서버 하나(`src/index.js`, 15,227줄)에 모든 게임이 등록** |
| DB·인증 | Supabase(Postgres + Auth). 서버는 service_role(`supabaseAdmin`)로만 DB 접근. 점수 테이블은 RLS 켜고 service_role만 허용 |
| 소켓 인증 | `io.use`(index.js:9543): 로그인은 JWT 검증, 게스트는 `guest_…` 아이디로 허용. IP 밴 검사 포함 |

### 1-2. 기존 멀티 게임의 실시간 방식 (중요)
- **굴려굴려·피해피해**: 각 클라이언트가 자기 물리를 계산하고 서버는 위치를 **그대로 중계**한다(golf.js 주석: "서버는 룸/홀 진행/Snapshot relay만, 물리 자체는 클라가 결정"). 서버 권위 판정이 아니다.
- **플듀 키우기 1대1(raising-pvp.js)**: 서버가 100ms마다 "여기까지 진행해도 됨"을 보내는 **결정적 락스텝**. 서버가 물리를 계산하지는 않는다.
- **도망도망(dodogo.js)**: 서버가 유령 AI만 `setInterval`로 돌린다. 유일한 서버 틱 사례.
- 결론: **서버가 매 틱 물리를 계산하는 구조는 이 프로젝트에 없다.** 차고차고는 새로 만든다. 단, 방·초대코드·재접속 같은 주변 구조는 그대로 재사용한다.

### 1-3. 방 구조 (golf.js / dodge.js 공통 패턴)
- 모듈 하나가 `Map` 3개(`rooms`, `invites`, `userRoom`)를 가지고, `registerXxx(io, supabaseAdmin)`을 index.js 맨 아래에서 호출.
- 이벤트는 `접두사:동작`(`golf:createRoom` …), 소켓 룸 이름은 `golf:${roomId}`.
- 방 만들기는 로그인 필요, 입장은 게스트도 가능. 6자리 초대코드. 방장이 나가면 다음 사람에게 방장 이전.
- 정리: 대기실에서 끊기면 즉시 퇴장, 경기 중 끊기면 자리 유지 + 전원 끊기면 `EMPTY_ROOM_TTL`(30초~2분) 후 방 삭제. 재접속은 같은 `userId`로 `joinRoom` 하면 `rejoined: true`.
- 닉네임·아바타는 profiles 테이블을 서버가 조회(닉네임 = 프로필 우선 원칙).

### 1-4. 클라이언트 소켓 (`js/lifegame-multi-socket.js`)
- `connect()`, `emitWithAck()`, `getSocket()`, `getAuthInfo()` 제공. 게스트 id는 localStorage에 저장.
- 전송 방식 `["polling","websocket"]`. 차고차고는 **websocket 단독**으로 연결해야 한다(폴링으로 시작하면 입력 지연).

### 1-5. 점수 · 랭킹
- `dodge_scores` 등: id, user_id, guest_id, nickname, score, flagged, client_run_id(중복 제출 방지 유니크), created_at. 조회 API `/dodge/leaderboard/{global,daily,me}`.
- 차고차고는 점수제가 아니라 승패제이므로 **별도 스키마**(6단계)가 필요. 기존 테이블은 건드리지 않는다.

### 1-6. 모바일
- 각 게임 HTML이 `viewport … user-scalable=no`, 게임별 CSS(`*-v2.css`)로 대응. 공통 입력 라이브러리는 없음 → 차고차고 전용 조이스틱/버튼 컴포넌트를 새로 만든다.

### 1-7. AI 봇 (omok-bot.js)
- 서버 순수 함수 + `LEVELS = {easy, normal, hard}` 매개변수 표(정확도·노이즈·깊이). 방 상태를 읽기만 하고 실제 착수 검증은 게임 모듈이 한다.
- 차고차고 봇도 같은 원칙: **봇은 사람과 같은 입력 구조(`mx,my,ax,ay,shoot,pass,dash,tackle`)만 만들어 낸다.** 물리·규칙은 동일하게 적용.

### 1-8. 주의할 기존 제약
| 항목 | 내용 | 대응 |
|---|---|---|
| 소켓 한도 | `safeOn`은 IP당 10초 30이벤트. 입력은 초당 30번 | 차고차고 입력 이벤트는 `safeOn`을 쓰지 않고 소켓별 자체 한도(초당 60) 사용 |
| 한 프로세스 | 모든 게임이 한 이벤트 루프를 공유 | 방마다 `setInterval`을 두지 않고 **전역 스케줄러 1개**가 모든 방을 순서대로 진행(드리프트 보정) |
| IP 공유 | 학교·PC방은 한 IP | IP 기준 제한은 쓰지 않고 소켓·유저 기준 |
| RLS | 새 테이블은 만들자마자 RLS(기억된 교훈) | 6단계 마이그레이션에 포함 |

## 3. 전체 아키텍처

```
브라우저                                   Render 서버 (기존 index.js 프로세스)
┌───────────────────────────┐             ┌────────────────────────────────────┐
│ chago.html                │ websocket   │ chago.js  (registerChago)          │
│  ├ 입력(키보드/터치)      │ ─input 30Hz→│  ├ 방·팀·대기실·재접속              │
│  ├ 예측: 내 선수 1명      │             │  ├ 전역 스케줄러 30Hz (모든 방)     │
│  ├ 보간: 공·다른 선수     │ ←snapshot── │  ├ chago-match.js  규칙/타이머/연장 │
│  ├ 렌더(canvas)·UI·사운드 │   20Hz      │  ├ chago-engine.js 물리 (권위)      │
│  └ chago-engine.js(복사본)│             │  └ chago-bot.js    봇 입력 생성     │
└───────────────────────────┘             └──────────────┬─────────────────────┘
                                                         │ 경기 종료 시 1회
                                                         ▼
                                              Supabase: chago_matches / chago_stats
```

원칙
1. **서버만 진실**: 공 위치·소유·킥·태클·골·점수·시간은 서버만 결정. 클라이언트는 "무엇을 누르고 있는지"만 보낸다.
2. **같은 엔진 파일**을 서버와 브라우저가 공유(`chago-engine.js`는 의존성·시간·난수가 없는 순수 코드). 브라우저는 내 선수의 이동 예측에만 쓴다.
3. 기존 서비스 변경은 **index.js에 import 1줄 + register 1줄**, gamezone 카드 1개로 한정.

## 5. 멀티플레이 네트워크 설계

### 5-1. 이벤트 (접두사 `chago:`)
| 방향 | 이벤트 | 내용 |
|---|---|---|
| C→S | `createRoom` / `joinRoom` / `leaveRoom` / `requestState` | 기존 패턴 동일(ack 콜백) |
| C→S | `setConfig` | 방장만, 대기실만: `teamSize`(1~4), `durationSec`(120/180/300), `mode`(friendly), `botLevel`, `fillBots` |
| C→S | `setTeam` | 팀0/팀1 이동(정원 확인) |
| C→S | `kickPlayer` / `startGame` | 방장 |
| C→S | **`input`** | 아래 5-2. `volatile`(밀리면 버림) |
| S→C | `roomState` | 대기실·경기 설정·참가자(사람/봇) |
| S→C | `matchState` | 단계·시계·점수(값이 바뀔 때만) |
| S→C | **`snap`** | 물리 스냅샷 `{k, b:[x,y,vx,vy,spin], p:[[슬롯,x,y,vx,vy,각도,스태미나,차지,상태비트,ack],…]}` |
| S→C | `ev` | kick/goal/tackleHit/post/whiff 등(효과음·이펙트용) |
| S→C | `roomClosed` / `kicked` | 기존과 동일 |

### 5-2. 입력 프로토콜
```
{ s: 시퀀스번호, mx, my: -1~1, ax, ay: 조준벡터, f: 비트(1=슛 누름 2=패스 누름 4=대시 8=태클) }
```
- 클라: 30Hz로 전송(상태가 같아도 매 틱 — 손실 복구가 단순). 약 20바이트.
- 서버: 소켓별 최신 입력 1개 보관. 틱마다 그 입력을 적용. **150ms 넘게 새 입력이 없으면 마지막 입력 유지 → 250ms 넘으면 중립 입력**(계속 달리는 버그 방지).
- 시퀀스가 과거이거나 형식이 틀리면 버림. 값은 `cleanInput`이 전부 정규화(NaN/무한대/거대한 값 → 안전한 값). 이동 속도는 서버가 계산하므로 **클라가 속도를 조작할 방법이 없다**.
- 소켓별 한도 초당 60개 초과분 버림, 지속 초과 시 경고 후 킥.

### 5-3. 스냅샷
- 서버 시뮬 30Hz, **스냅샷 전송 20Hz**(설정값). 같은 소켓룸 전원에게 1개를 만들어 전송.
- 크기: 선수 id를 uuid로 쓰면 8명 571B, **슬롯 번호(0~7)로 쓰면 275B**. 2단계에서 슬롯 번호 방식으로 바꾸고, 필요하면 바이너리(약 150B)로 줄인다.
- 대역폭 추정(4대4, 20Hz, JSON 275B): 방 1개 약 44KB/s(클라 8명 × 5.5KB/s). 방이 동시에 20개여도 약 0.9MB/s. Render 대역폭 상한을 6단계 전에 확인한다.
- `volatile.emit`으로 보내 느린 연결에서 스냅샷이 쌓이지 않게 한다.

### 5-4. 클라이언트 보정
- **다른 선수·공**: 100ms 뒤 시점으로 보간(스냅샷 2~3개 버퍼). 끊기면 최대 200ms까지 속도로 외삽.
- **내 선수**: 입력 즉시 로컬 엔진으로 이동 예측 → 서버 스냅샷의 `ack`(마지막 반영 시퀀스)와 비교해 어긋나면 그 지점부터 저장해 둔 입력을 다시 적용(reconciliation). 오차가 작으면 부드럽게 수렴, 크면(≥60px) 즉시 맞춤.
- **킥/태클**: 서버 판정이라 공이 움직이기까지 왕복 지연(RTT)이 있다. 누르는 즉시 **킥 모션·소리는 로컬로 재생**하고 공 반응만 서버를 따른다. 체감이 나쁘면 2단계 측정 후 "서버가 킥 입력의 클라이언트 시각을 인정해 한두 틱 되감아 판정"하는 지연 보상을 검토한다.
- 공은 예측하지 않는다(서버 값만 사용). 이유: 소유 판정이 서버 권위이고, 잘못된 예측이 "공이 순간이동"으로 보이는 걸 막기 위해.

### 5-5. 방 · 재접속 · 퇴장
| 상황 | 처리 |
|---|---|
| 대기실에서 끊김 | 기존처럼 즉시 퇴장(방장이면 이전) |
| 경기 중 끊김 | 자리 유지, 입력 중립, **10초 안에 같은 userId로 `joinRoom`이면 같은 선수로 복귀**(`rejoined`) + 현재 스냅샷 즉시 전송. 10초 넘으면 그 자리를 **봇이 대체** |
| 자발 퇴장 | 즉시 봇 대체. 사람이 0명이면 방 종료 |
| 한 계정 다중 접속 | `userRoom` 맵으로 방 1개만. 새 소켓이 기존 소켓을 대체 |
| 빈 방 | 전원 끊김 60초 후 삭제(타이머·Map 항목 정리) |
| 중도 입장 | 경기 중에는 **봇이 있는 팀의 봇 자리**에 한해 허용. 교체는 득점 후 세레머니 중이거나 봇이 공에서 400px 이상 멀 때, 최대 5초 대기 |
| 방 종료 | 모든 `Map`, 타이머, 소켓룸 해제 |

### 5-6. 부정행위 방지
- 서버가 속도·충돌·킥을 직접 계산 → 속도핵·순간이동·공 조작·점수 조작 불가.
- 남는 위험: **자동 조준/매크로**(입력 자체가 정상) → 6단계에서 입력 패턴 로그와 신고로 대응. 경쟁전은 이 대응이 끝나기 전까지 열지 않는다.

## 6. 공과 선수의 물리 판정 설계 (1단계에서 구현)

### 6-1. 시간
- 서버 틱 **30Hz(DT=1/30)**, 한 틱을 **4번 쪼개 120Hz로 계산**. 공 최대속도 1100px/s → 서브스텝당 9.2px < 공 반지름 11px 이므로 **어떤 속도에서도 벽·선수를 뚫지 못한다**(무작위 240회 발사 시험으로 확인).

### 6-2. 수치 (현재 기본값, `PHYS` 상수 한 곳에서 조정)
| 항목 | 값 |
|---|---|
| 선수 반지름 / 공 반지름 | 20 / 11 px |
| 걷기 / 대시 | 250 / 375 px/s |
| 가속 / 감속 | 2600 / 3400 px/s² |
| 스태미나 | 100, 대시 초당 -38(≈2.6초), 회복 초당 +20(0.6초 뒤부터), 바닥나면 25까지 대시 불가 |
| 공 감속 | 지수 감쇠 0.75/s + 구름 저항 40px/s² |
| 공 반사 | 벽 0.78, 골포스트 0.85, 선수 0.55 |
| 슛 | 최소 360 ~ 최대 1050 px/s(×경기장 배율), 풀차지 0.85초, 차징 중 이동속도 72% |
| 슛 이동 반영 | 선수 속도의 35%가 공에 더해짐 |
| 커브 | 조준선에 수직으로 달리며 차면 반대쪽으로 휘는 마그누스(최대 1.0) |
| 패스 | 조준 원뿔 ±38° 안(없으면 ±70°)의 가장 좋은 팀원. 짧게 누름 = 일반, 0.28초 이상 = 스루(0.55초 앞을 예측) |
| 킥 조건 | 발이 닿는 거리 + **조준 방향 앞쪽 ±105° 안**에 공이 있어야 함(몸 뒤 공은 헛발질) |
| 킥 쿨다운 | 0.28초 |
| 태클 | 560px/s로 0.22초 돌진, 적중 시 상대 0.55초 기절 + 공 튕김 430px/s, 쿨다운 1초, 스태미나 22, 헛스윙 회복 0.35초(적중 0.2초) |
| 경기장 | 1v1 900×520 / 2v2 1000×580 / 3v3 1100×640 / 4v4 1200×700, 골문 170~230 |
| 킥 배율 | 1v1 0.82 · 2v2 0.9 · 3v3 0.95 · 4v4 1.0 (작은 경기장이 정신없지 않도록) |

체감 기준(측정): 4대4에서 풀슛 자유 비행 약 1,180px(경기장 길이와 비슷), 가로 횡단 걷기 4.8초/대시 3.2초.

### 6-3. 충돌 처리 순서 (서브스텝마다)
이동 → 공 이동(마찰·마그누스) → 선수-선수 → 태클 접촉 → 공-선수 → 선수-벽 → 공-벽·포스트 → **끼임 해소** → 골 판정.
- 선수-선수: 같은 질량 반발 0.2, 겹침은 반반 밀어냄(태클 돌진 중인 쪽은 안 밀림).
- 공-선수: 공이 일방적으로 밀려나고(선수는 조종값 유지) 공에 반발 임펄스. **공이 벽과 선수 사이에 끼면 선수가 물러난다** → 공이 달라붙거나 떨리거나 순간이동하지 않음.
- 골 판정: 공 **전체**가 골라인을 넘고 골문 범위 안일 때 1회. 포스트는 원, 골대 안쪽 벽·그물은 선분. 선수는 골문 입구가 막혀 있어 골대에 못 들어감.
- 득점자·자책 판정: 마지막으로 공을 건드린 선수 기준.

### 6-4. 소유권
별도의 "공 붙이기"는 없다. **마지막 접촉자(`lastTouch`)**와 접촉 시각을 서버가 기록하고, 킥은 서버가 거리·방향·쿨다운을 검사해 허용한다. (클라이언트가 "내가 찼다"고 주장할 방법이 없다.)

### 6-5. 경기 규칙 (`chago-match.js`)
카운트다운 3초(전원 정지) → 경기 → 골(세레머니 3초, 시계 정지) → 킥오프(실점 팀) …
시간 종료 시 점수가 다르면 종료, 같으면 모드별:
| 모드 | 연장 | 연장 후에도 동점 |
|---|---|---|
| 친선(friendly) | 골든골 90초 | **무승부** |
| 경쟁(ranked) | 골든골 90초 | **승부차기** — 5단계 구현 전까지 **열지 않음**(`RULES.ranked.enabled=false`) |
종료 직전 터진 골은 인정하고, 세레머니 후 종료 판정.

## 7. AI 봇 구조 (3단계)

- **입력 생성기**: `botThink(match, botId, level, rng) → input`. 사람과 같은 입력 구조, 같은 물리·쿨다운·스태미나 적용(치트 없음).
- **판단 주기**: 쉬움 250ms / 보통 150ms / 어려움 80ms마다 재판단, 그 사이에는 이전 결정 유지. **반응 지연**(입력 지연) 250 / 150 / 60ms.
- **역할**(슬롯 기준): 키퍼형(골대 앞 라인 따라 이동, 슛 궤적 차단) · 수비 · 공격. 1v1은 한 명이 모든 역할.
- **떼 지어 공만 쫓는 문제 방지**: 팀원 중 "공 도착 예상 시간이 가장 짧은 1명"만 **추격자**, 나머지는 포메이션 위치(공 위치에 따라 앞뒤로 밀고 당김) + 패스 받을 빈 공간으로 이동. 추격자는 0.5초마다만 재선정(깜빡임 방지).
- **공 가졌을 때**: 슛 가능(골문 각도·거리·가로막는 선수 없음) → 슛(차징 시간은 거리 비례). 아니면 패스 점수(전진 거리 + 받는 사람이 열려 있는 정도) 비교 → 패스. 아니면 골대 쪽으로 드리블. 압박받으면 패스/태클 회피.
- **수비**: 공 가진 상대와 골대 사이로 이동, 일정 거리 안에서 확률적으로 태클(난이도별 확률·쿨다운 존중).
- **난이도 매개변수 표**(omok-bot 방식): `{ reaction, thinkMs, aimNoiseDeg, dashUse, tackleChance, passSkill, shootRange, keeperReach }`.
- **중도 교체**: 사람이 들어오면 봇 → 사람으로 같은 선수 객체의 제어권만 바꾼다(위치·스태미나 유지).
- 검증: 봇끼리 수천 경기 시뮬레이션으로 득점 분포, 한 곳 몰림, 멈춤 현상 측정.

### 구현

- 행동: 공 예측 접근(공 뒤로 돌아 들어가기), 슛(상대 키퍼에서 먼 골문 구석·길이 열렸을 때·필요한 만큼만 차징), 패스(앞쪽·열린 팀원, 키퍼에게는 안 줌), 드리블, 태클, 키퍼(골문 라인 이동·슛 경로 차단·걷어내기), 벽·구석에 붙은 공 빼내기, 공 옆 자리 찾아 차기

### 시뮬레이션이 잡아낸 결함 (고친 것)
0. (마지막 단계) 서로 같은 공을 두고 맴도는 **대치**, 구석에서 조준이 공 뒤쪽으로 틀어져 헛발질 반복 → 대치 5회 감지 시 직접 부딪혀 밀기, 구석 탈출 시 실제 선 자리 기준으로 조준 재계산
1. **엔진: 공이 경기장 밖으로 빠져나감** — 선수 여럿이 벽 쪽에서 공을 누르면 공을 밀어내는 계산이 공을 벽 너머로 보냈다(공이 y=-96에 100초 정지). → 매 서브스텝 마지막에 공을 경기장·골대 안으로 되돌리는 안전장치(`containBall`) + 회귀 테스트
2. **봇이 굴러가는 공 뒤에서 밀며 쫓아가 자기 골대로 몰고 감** — 득점의 약 80%가 이 방식이었다. → 공이 갈 위치를 예측해 "공을 보내고 싶은 방향의 반대편"으로 돌아 들어가 접근
3. 구석·벽에 붙은 공을 못 빼내 10~40초 동안 공이 멈춤 → 공 둘레 자리를 탐색해 공이 조준 앞쪽에 들어오는 옆자리에서 비스듬히 차 내는 루틴
4. 봇이 공이 몸 뒤에 있는 채로 슛을 걸어 헛발질 반복 → 먼저 공 뒤로 돌아간 뒤 차기
5. 봇이 슛 차징 중 공이 굴러가 헛발질 → 차징 중 공을 따라붙고, 상대가 바짝 붙었으면 길게 차징하지 않음
6. 키퍼에게 되돌려주는 패스가 자책골로 이어짐 → 키퍼는 패스 대상에서 제외, 뒤쪽 패스 금지

### 알려진 한계 (정직하게)
- 구석·벽에서 봇이 잠깐(최대 2.5초) 머뭇거리다 빠져나오는 경우가 있다. 최종 상태에서 인원별 60경기씩 시뮬레이션했을 때 공 최장 정지는 1.3~2.5초였다(중간에 63초 정지가 나온 적이 있어, 대치 감지·벽 우선 처리·조준 재계산을 추가해 해결).
- 어려움 봇은 보통보다 확실히 강하지만, **사람 상대로 얼마나 재미있는지는 실제 플레이 시험이 필요**하다(수치는 봇끼리의 결과).
- 선수끼리 몸이 부딪히는 순간 내 화면 예측과 서버 위치가 최대 약 30~50px 어긋났다가 부드럽게 맞춰진다(강제 순간이동은 0회). 4단계 이후 더 줄일 수 있음.
- 경기 중 입장자는 최대 5초 대기 후 합류. 관전 모드는 6단계.
- 서버 위치 문제(왕복 약 200ms)는 그대로이며 사용자 결정 대기 중(12장).

## 16. 6단계 — 운영 (기록 · 랭킹 · 관전 · 신고 · 관리자)

### DB (`sql/schema_chago.sql`, 롤백 `sql/rollback_chago.sql`) — **운영 DB에 아직 적용 안 함**
- 테이블 4개: `chago_matches`(경기), `chago_match_players`(경기별 선수), `chago_ratings`(시즌별 레이팅), `chago_reports`(신고). 모두 RLS 켜짐, service_role 만 접근.
- 함수 `chago_apply_match(m jsonb, pl jsonb)`: 경기 기록 + 레이팅 증감을 한 번에 처리. (room_id, started_at) 유니크로 중복 기록 방지, 증감식 갱신이라 동시 경기에도 안전. public/anon/authenticated 실행 권한 회수.
- 기존 테이블·멀티·채팅과 연결(FK/트리거) 없음. 원자적 DO 블록 + 의도적 예외로 운영 DB에서 흔적 없이 사전 검증함.
- 서버는 테이블이 없으면 기록만 건너뛰고 게임은 정상(60초마다 재확인 → SQL 적용 후 재시작 불필요).

### 랭킹 규칙 (`chago-rank.js`)
- Elo, K=32(경쟁전 10경기 미만) → 20. 월 단위 시즌(KST), 순위 표시는 경쟁전 3경기 이상.
